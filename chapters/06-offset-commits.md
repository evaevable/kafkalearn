# 第 6 章：Offset 提交——重启之后，从哪继续读？

> 上一章：消费组把分区"分"给队员。这一章只有一个问题：队员突然掉线，新队员凭什么知道从哪继续？
> 答案就一个词：**书签**。本章实验让 4 个消费者在 4 个不同时刻"猝死"，看分别会出什么事。

## 【积木 6-1】先解决一个实际问题

想象你在看一本很长的书，看到第 30 页，要出门吃饭。回来怎么接着看？

- 靠记忆：万一忘了，只能从头翻。
- 夹个书签：回来直接翻到书签那一页。

Kafka 消费者面对的是同一个问题。分区日志就像一本不断往后加页的书：

- 什么都不记 → 程序重启后不知道读到哪了，只能重新读。
- 把位置记下来 → 重启后接着读。

这个记下来的位置，就叫 **committed offset**（已提交位移，俗称"提交"）。它保存在 Kafka 这边，按 **消费组 + 主题 + 分区** 分别记录。哪怕第二天换了一台机器、换了一个进程，只要还是同一个消费组，就能读到这份书签。

顺便分清两个东西：**每条消息在它所属分区里自带一个编号（offset），像印在书页上的页码；书签是读者另外夹进去的**，两者不是一回事——消费者能改的只有自己的书签。

（回答一个高频疑问：**存书签不删除消息，读消息也不删除消息**，跟前面几章的结论一致。）

## 【积木 6-2】三个"到哪了"，先别混

同一个消费者身上，同时跑着三个进度，特别容易搅浑：

| 进度 | 大白话 |
| --- | --- |
| position（读取位置） | 我眼睛看到哪了——刚读完第 0 条，下一眼看第 1 条 |
| 处理进度 | 我的活干到哪了——第 0 条订单的库存扣完了 |
| committed（书签） | 我记到 Kafka 上的位置——"下次从 1 开始读" |

一句话：**眼睛看到哪 ≠ 活干完了 ≠ 书签存好了。**

本章要干的事，就是故意让程序在"这三个不同步"的时刻死掉，看会出什么事。

```mermaid
flowchart LR
    A["读到 offset 0"] --> B["干活：处理订单"]
    B --> C["存书签：1"]
    C -.->|"重启"| D["从 offset 1 继续"]
```

## 【积木 6-3】书签的规矩：记"下一条"

只需要记一条规矩：

**书签记的是"下一条从哪读"，不是"刚读到哪条"。**

- 处理完 offset 0 → 书签存 **1**
- 处理完 offset 0 到 9 → 书签存 **10**

为什么？因为书签的用途是回答"重启后从哪开始读"。存 1，就是"下次从 1 读起"。

还有一个容易乱的地方：

**"从没存过书签" ≠ "存了 0"。**

- 从没存过：Kafka 不知道你读到哪，只能按规则来（`auto.offset.reset=earliest` 从头读，`latest` 只读新消息）。
- 存了 0：明确表态"我要从头读"。

## 【积木 6-4】三种"死法"

"读完一条消息后，先干活还是先存书签？"——就这一个决定，决定了程序崩溃时发生什么。

实验里每条分区日志只有 3 条消息（offset 0、1、2）。4 个组的消费者都先读到 offset 0，然后分别在 4 个时刻猝死：

| 死前干了什么 | 重启后从哪读 | 结果 |
| --- | --- | --- |
| 只读到，没干活，没存书签 | offset 0 | 重读，然后补干 |
| 干完了活，没存书签 | offset 0 | 重读重干（重复） |
| **先存了书签，还没干活** | offset 1 | offset 0 的活永远没人干（**漏**） |
| 干完活，也存好书签 | offset 1 | 正常继续 |

实验的最终数据（每个 offset 的"活"被干了几次）：

| 组 | 重启从哪读 | offset 0 / 1 / 2 干活次数 |
| --- | --- | --- |
| 只读不干 | 0 | 1 / 1 / 1 |
| 干了不存 | 0 | **2** / 1 / 1 |
| 存了不干 | 1 | **0** / 1 / 1 |
| 干完再存 | 1 | 1 / 1 / 1 |

三条结论：

1. **没存书签 → 重读重干，但不漏活。**
2. **先干活再存书签 → 崩溃时可能重复干活，但不漏活。**
3. **先存书签再干活 → 会漏活，而且程序自己发现不了。**

第三行最危险。"存了不干"那个组，最后的积压（Lag）显示为 0，看起来"全读完了、全处理完了"，其实 offset 0 的活根本没干过。

**Lag 只代表"读到哪了"，不代表"活干完了"。**

## 【积木 6-5】那到底怎么选？

工程上的通行取舍只有一句话：

> **宁可重复，不要漏。**

一笔订单处理两次（配合业务上的防重手段）通常可以接受；一笔订单永远没人处理，通常不可接受。

所以标准姿势是：

**先干活 → 干成功 → 再存书签。**

这就是常说的**"至少一次"（at-least-once）**：活至少干过一次，代价是崩溃时可能重复。

反过来，"先存书签再干活"叫**"最多一次"（at-most-once）**——跑得快，但会漏。除非业务明确允许丢消息，否则别用。

那"重复"怎么解决？让业务能安全地重复执行——比如扣库存前先查一下这笔订单扣过了没有。这是"幂等"话题，第 11 章专门拆。

## 【积木 6-6】代码里的两个开关，别搞混

Consumer 默认有两个"自动"帮你干活，而且默认都开着：

| 开关 | 干了什么 |
| --- | --- |
| `enable.auto.offset.store` | 消息一交到你手上，就自动记"这个位置可以当书签" |
| `enable.auto.commit` | 每隔几秒，把"可以当书签的位置"存到 Kafka |

坑在哪：**消息刚交到你手上，你什么活都还没干，它就已经被记成"可以当书签"了。**这时候崩溃，没干完的活对应的位置已经被存成书签，重启直接跳过 → 漏活。

所以生产代码的常见做法是：**关掉自动的，手动控制**。本章实验把两个开关都关掉，处理成功后再手动存：

```python
# 干完活，再存书签；commit 会提交"这条消息的位置 + 1"
consumer.commit(message=msg, asynchronous=False)
```

`message=msg` 帮我们省去手动加一；`asynchronous=False` 表示"等 Kafka 确认存好了再往下走"，比不等确认（`asynchronous=True`）更直观。

注意：手动提交也只是减少出错概率，**"干完活"和"存书签"之间仍然有一条缝**——正好死在这条缝里，还是会重复。这就是为什么业务侧还要防重。

## 【积木 6-8】自测

先回答，再展开答案：

1. 书签存的是"刚读完的那条"，还是"下一条"？读完 offset 5、处理成功，应该存几？
2. "从来没存过书签"和"存了 0"，是一回事吗？
3. 先存书签再干活，突然崩溃，会怎样？先干活再存书签呢？
4. 为什么说"宁可重复，不要漏"？对应哪两种英文叫法？
5. 自动提交的坑是什么？两个"自动"开关分别管什么？
6. 手动提交能保证"干完活"和"存书签"变成一件事吗？
7. Lag 显示 0，能说明所有活都干完了吗？举本章的反例。
8. 提交书签会删除消息吗？

<details>
<summary>展开参考答案</summary>

1. 存"下一条"。读完 5 并处理成功，应存 6。
2. 不是。没存过是"未知"，Kafka 只能按 auto.offset.reset 的规则决定从哪读；存 0 是"明确要从头读"。
3. 先存后干：重启跳过没干的活，**漏**。先干后存：重启重读重干，**重复但不漏**。
4. 重复可以通过业务防重消化，漏掉往往无法察觉、无法补救。分别叫 at-least-once 和 at-most-once。
5. 消息刚交付就被自动标记为"可提交"，活没干完书签可能已存走，崩溃就漏。auto.offset.store 管"标记位置"，auto.commit 管"定期提交"。
6. 不能。两步之间仍有窗口，正好死在窗口里还是会重复；所以业务侧还要幂等防重。
7. 不能。"存了不干"那组 Lag=0，但 offset 0 的活从没干过。Lag 只反映"读到哪了"。
8. 不会。提交只是存进度，读也不会删；删消息是保留策略的事。

</details>
